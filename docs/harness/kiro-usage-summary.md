# Kiro + 하네스 엔지니어링 적용 정리

작성일: 2026-08-28

## 1. 한 줄 요약

이번 프로젝트는 `Kiro 기반 Spec-Driven 작업 방식`에 `하네스 엔지니어링` 개념을 결합해, AI와 백엔드 구현이 요구사항 밖으로 벗어나지 않도록 통제하는 구조로 운영했다.

## 2. 하네스 엔지니어링이란 무엇인가

하네스 엔지니어링은 AI가 바로 코드를 만들어내도록 두는 것이 아니라, 먼저 `요구사항`, `설계`, `작업 범위`, `검증 기준`을 고정해서 AI가 그 틀 안에서만 움직이도록 만드는 방식이다.

쉽게 말하면 다음과 같다.

- AI에게 바로 구현을 맡기지 않는다.
- 먼저 기준 문서를 만든다.
- 작업 단위를 나눈다.
- 허용 범위와 금지 범위를 정한다.
- 검증 기준을 통과한 결과만 다음 단계로 넘긴다.

즉, AI를 자유롭게 두는 것이 아니라 `프로젝트 목적에 맞게 안전하게 묶어두는 운영 장치`가 바로 하네스다.

## 3. 왜 이번 프로젝트에 필요했는가

`RoomPACT Campus`는 단순한 CRUD 프로젝트가 아니다.

- 생활 인터뷰 수집
- Hardcut 조건 반영
- 캐릭터 유형 분류
- 추천 후보 계산
- 상호 수락 기반 채팅
- 룸메이트 확정 후 약속 생성
- AWS 기반 배포
- 생성형 AI 활용

이런 프로젝트는 아이디어와 구현이 쉽게 섞이고, AI 기능 범위도 금방 커진다. 해커톤에서는 특히 시간이 짧기 때문에, 바로 구현에 들어가면 아래 문제가 생기기 쉽다.

- 요구사항과 구현이 어긋남
- 프론트, 백엔드, AI 역할이 섞임
- 생성형 AI가 불필요한 결정까지 맡게 됨
- 발표 때 왜 이런 구조로 만들었는지 설명이 어려워짐

그래서 이번 프로젝트는 처음부터 `Kiro + 하네스 엔지니어링` 방식으로 관리했다.

## 4. Kiro를 어떻게 하네스로 사용했는가

이번 프로젝트에서 Kiro는 단순 문서 정리 도구가 아니라, `프로젝트의 기준을 고정하는 하네스 시스템`으로 사용되었다.

핵심 문서 구조는 아래와 같다.

- `.kiro/specs/roompact-campus/requirements.md`
  - 무엇을 만들어야 하는지 정의
- `.kiro/specs/roompact-campus/design.md`
  - 어떻게 만들지 정의
- `.kiro/specs/roompact-campus/tasks.md`
  - 어떤 순서와 단위로 구현할지 정의
- `.kiro/steering/product.md`
  - 서비스 방향과 가치 정의
- `.kiro/steering/tech.md`
  - 기술 선택과 개발 원칙 정의
- `.kiro/steering/structure.md`
  - 디렉토리 구조와 파일 배치 원칙 정의
- `AGENTS.md`
  - 모든 AI 에이전트가 따라야 하는 공통 작업 규칙 정의

즉, Kiro 문서 세트가 이 프로젝트의 `Single Source of Truth` 역할을 하도록 만들었다.

## 5. 실제 하네스 설계 포인트

이번 프로젝트에서 하네스 엔지니어링 관점으로 가장 중요했던 통제 지점은 아래와 같다.

### 5-1. Spec 선행 원칙

구현보다 먼저 아래 순서를 고정했다.

1. 요구사항 정의
2. 설계 정의
3. 작업 분해
4. 구현
5. 검증

이 원칙 덕분에 기능이 추가되거나 바뀔 때도 먼저 Spec을 보고 판단할 수 있었다.

### 5-2. AI 역할 제한

이번 프로젝트는 AI를 사용하지만, AI가 모든 결정을 하도록 두지 않았다.

문서에서 미리 아래처럼 역할을 제한했다.

- 점수 계산은 코드가 담당
- 매칭 결과 결정도 코드가 담당
- 갈등 순위 판단도 코드가 담당
- LLM은 갈등 시나리오 생성, 협상안 문장화, Pact 문장 생성에만 사용
- Gemini API 호출은 `llm_client.py` 한 곳으로 제한

이건 하네스 엔지니어링에서 가장 중요한 부분 중 하나다. AI를 `결정 주체`가 아니라 `제한된 생성 보조 도구`로 묶어둔 것이다.

### 5-3. 작업 단위 통제

`tasks.md`에서 구현을 작은 단위로 나누고 각 Task에 아래 정보를 붙였다.

- ID
- Status
- Requirement
- Acceptance
- Verify
- File Scope
- Depends on

이렇게 해두면 AI가 한 번에 너무 넓은 범위를 건드리지 못하고, 사람이 봐도 어디까지 끝났는지 바로 확인할 수 있다.

### 5-4. 파일 경계 통제

이번 구조에서는 파일 역할도 문서에서 먼저 고정했다.

예를 들면:

- `scoring.py`: 점수 계산 전용
- `matching.py`: 매칭 계산 전용
- `llm_client.py`: Gemini API 호출 전용
- `fallback.py`: LLM 실패 시 결정론적 대체 응답 전용

이렇게 모듈 책임을 미리 분리해 두면, 구현 중에 책임이 섞이는 것을 줄일 수 있다.

### 5-5. 검증 루프 유지

하네스는 문서만 있다고 완성되지 않는다. 결과를 확인하는 루프가 있어야 한다.

그래서 아래 운영 규칙도 같이 뒀다.

- verify 스크립트 사용
- Hook 최소화
- handoff 기록 유지
- Acceptance 충족 전 DONE 금지

즉, 구현 결과가 문서 기준에 맞는지 계속 확인하는 구조로 운영했다.

## 6. 이번 프로젝트의 실제 작업 흐름

실제 운영 흐름은 아래처럼 정리할 수 있다.

1. 서비스 아이디어를 정리한다.
2. `requirements.md`에서 범위와 제약을 고정한다.
3. `design.md`에서 아키텍처와 모듈 책임을 고정한다.
4. `tasks.md`에서 P0/P1 기준으로 구현 단위를 나눈다.
5. AI 에이전트와 개발 작업은 그 Task를 따라 진행한다.
6. 구현 후 검증과 배포를 수행한다.
7. 변경 요청이 생기면 코드를 바로 바꾸지 않고 먼저 Spec과 정합성을 확인한다.

이 흐름이 바로 Kiro를 하네스로 사용한 방식이다.

## 7. 기획자 관점에서 얻은 효과

기획자 입장에서 이 방식의 장점은 분명했다.

### 7-1. 기능 우선순위가 선명해진다

P0와 P1을 구분해서 관리했기 때문에, 시연에 꼭 필요한 기능과 후속 기능을 명확히 나눌 수 있었다.

### 7-2. 설명 가능한 AI 구조가 된다

심사에서는 "AI를 썼다"보다 "왜 여기서 AI를 썼는가"가 더 중요하다. 이번 구조는 AI 사용 범위를 문서로 제한했기 때문에, AI 활용의 적절성을 설명하기 쉬웠다.

### 7-3. 역할 분담이 쉬워진다

프론트, 일반 백엔드, AI 백엔드가 어떤 책임을 가지는지 문서 기준으로 정리되어 있어 협업 경계가 명확해졌다.

### 7-4. 변경 대응력이 좋아진다

중간에 요구사항이 바뀌어도 전체 구조가 흔들리지 않았다. 먼저 Spec을 확인하고, 그 다음 구현을 조정하는 방식으로 대응할 수 있었다.

## 8. 이번 프로젝트에서의 의미

정리하면 이번 프로젝트에서:

- `Kiro`는 Spec을 관리하는 기준 시스템이었고
- `하네스 엔지니어링`은 그 Spec을 이용해 AI와 구현 범위를 통제하는 운영 방식이었다

즉, 둘은 따로 쓰인 개념이 아니라 함께 작동했다.

`Kiro가 문서 기반 기준을 제공하고`, `하네스 엔지니어링이 그 기준을 실제 개발 통제 장치로 작동하게 만든 것`이다.

## 9. 최종 정리 문장

기획자에게는 아래처럼 설명하면 된다.

> 이번 프로젝트는 Kiro 기반 Spec-Driven 개발 방식을 사용했고, 이를 하네스 엔지니어링 방식으로 운영했다.  
> 즉, 요구사항, 설계, 작업 범위, 검증 기준을 먼저 문서로 고정한 뒤 AI와 백엔드 구현이 그 틀 안에서만 진행되도록 통제했다.  
> 이를 통해 해커톤 환경에서도 기능 우선순위, AI 활용 범위, 협업 경계, 발표 설명 구조를 안정적으로 유지할 수 있었다.
