# RoomPACT Campus Requirements

## 문서 목적

이 문서는 `RoomPACT Campus`의 기능 요구사항과 범위를 정의한다.
이 프로젝트는 대학 기숙사 2인실 룸메이트 배정을 지원하는 `일반 백엔드 + AI 백엔드` 구조를 대상으로 한다.

## 제품 목표

- 생활 패턴과 선호 조건을 바탕으로 2인실 룸메이트 배정을 계산한다.
- 배정 결과에 대해 학생이 이해할 수 있는 추천 이유를 제공한다.
- 잠재 갈등이 큰 조합에 대해서는 갈등 시나리오와 협상안을 생성한다.
- 최종 합의 규칙인 Pact 문구를 생성하되, LLM 장애 시에도 결정론적 fallback으로 응답을 유지한다.
- Gradio 프로토타입이 짧은 시연 안에 핵심 가치를 보여줄 수 있도록 AI 백엔드 결과를 제공한다.

## 범위

### 포함 범위

- 2인실 룸메이트 배정
- 네트워크X 기반 최소 비용 또는 최대 가중치 매칭 사용
- 갈등 시나리오 생성
- 협상안 문장화
- Pact 규칙 문장 생성
- LLM 실패 시 결정론적 fallback
- 일반 백엔드와 AI 백엔드의 분리 구조
- Gradio 프론트엔드가 호출할 수 있는 백엔드 응답 구조
- 두 백엔드가 함께 사용하는 최소 저장 구조

### 제외 범위

- 3인 이상 그룹 배정
- 자체 최적화 알고리즘 구현
- 점수 계산과 배정 결정을 LLM에게 위임하는 구조

## 시스템 제약

- 일반 백엔드와 AI 백엔드는 모두 Python으로 구현한다.
- AI 백엔드의 구현 파일 구성은 다음 모듈을 기준으로 한다.
  - `app.py`
  - `handler.py`
  - `scoring.py`
  - `matching.py`
  - `scenario.py`
  - `negotiate.py`
  - `pact.py`
  - `llm_client.py`
  - `fallback.py`
- 일반 백엔드는 별도 `app.py`와 라우트/서비스 계층을 가진다.
- AWS Bedrock 호출 코드는 `llm_client.py` 한 곳에만 둔다.
- `scoring.py`와 `matching.py`는 `llm_client.py`를 import하지 않는다.
- LLM 사용은 아래 3개 기능 경계 내에서만 허용한다.
  - 갈등 시나리오 생성
  - 협상안 문장화
  - Pact 규칙 문장 생성
- 일반 백엔드와 AI 백엔드는 공용 저장소를 사용할 수 있어야 한다.

## 사용자 시나리오

### US-01 배정 실행

운영자는 일반 백엔드에 학생 설문 응답 데이터를 전달하고, 시스템은 AI 백엔드를 통해 2인실 배정 결과를 반환해야 한다.

### US-02 추천 이유 확인

운영자 또는 학생은 각 배정 결과에 대해 왜 해당 조합이 추천되었는지 설명을 확인할 수 있어야 한다.

### US-03 갈등 대비

갈등 가능성이 있는 조합에 대해 시스템은 예상 갈등 시나리오와 협상 초안을 생성할 수 있어야 한다.

### US-04 Pact 생성

배정된 두 학생이 참고할 수 있도록 생활 규칙 Pact 문장을 생성할 수 있어야 한다.

### US-05 프로토타입 시연

시연자는 Gradio 화면에서 학생 입력 또는 샘플 데이터를 넣고, 배정 결과와 갈등 대응 결과를 순차적으로 확인할 수 있어야 한다.

### US-06 백엔드 연동

일반 백엔드는 공용 DB와 AI 백엔드를 사용해 입력 저장, AI 요청, 결과 조회를 연결할 수 있어야 한다.

## 기능 요구사항

### FR-01 입력 처리

- FR-01.1 시스템은 학생 목록과 각 학생의 생활 패턴, 필수 조건, 선호 조건 데이터를 입력으로 받아야 한다.
- FR-01.2 시스템은 배정 가능한 학생 수가 짝수인지 검증해야 한다.
- FR-01.3 시스템은 필수 입력 필드 누락 시 명확한 오류를 반환해야 한다.
- FR-01.4 시스템은 학생 프로필 기본 정보로 `nickname`, `age`, `gender`, `region`, `move_in_period`, `stay_duration_months`를 저장하고 조회할 수 있어야 한다.
- FR-01.5 시스템은 학생 프로필별 생활 인터뷰 응답을 저장하고 조회할 수 있어야 한다.
- FR-01.6 시스템은 생활 인터뷰 응답을 기반으로 규칙성 점수, 공유성 점수, 4가지 캐릭터 유형을 코드로 산출하고 저장할 수 있어야 한다.
- FR-01.7 시스템은 생활 인터뷰를 제출한 프로필에 대해 자동 추천 후보를 계산하고 조회할 수 있어야 한다.
- FR-01.8 시스템은 추천 또는 확정 매칭된 두 프로필 사이에서 상호 수락이 완료된 경우에만 1:1 채팅방을 생성하고 조회할 수 있어야 한다.
- FR-01.9 시스템은 채팅방별 최근 메시지 이력을 저장하고 다시 불러올 수 있어야 한다.
- FR-01.10 시스템은 추천 후보 간 대화 시작 전 매칭 요청 생성과 상대 수락 상태를 저장하고 조회할 수 있어야 한다.

### FR-02 점수 계산

- FR-02.1 시스템은 각 학생 쌍에 대해 코드 기반 호환 점수를 계산해야 한다.
- FR-02.2 시스템은 필수 조건이 충돌하는 학생 쌍을 배정 후보에서 제외해야 한다.
- FR-02.3 시스템은 선호 조건과 가중치를 사용해 쌍별 점수를 산출해야 한다.
- FR-02.4 점수 계산은 결정론적이어야 하며 동일 입력에 대해 동일 결과를 반환해야 한다.
- FR-02.5 점수 계산 로직은 LLM 또는 외부 네트워크 호출에 의존하면 안 된다.

### FR-03 배정 계산

- FR-03.1 시스템은 `networkx`의 매칭 API를 사용해 전체 학생 집합의 2인실 배정을 계산해야 한다.
- FR-03.2 시스템은 직접 작성한 최적화 알고리즘으로 배정을 계산하면 안 된다.
- FR-03.3 시스템은 한 학생이 정확히 한 쌍에만 속하도록 보장해야 한다.
- FR-03.4 시스템은 배정 불가능한 경우 원인과 함께 오류 또는 상태를 반환해야 한다.
- FR-03.5 배정 결과는 점수 요약과 추천 이유 생성에 필요한 근거 데이터를 포함해야 한다.

### FR-04 결과 설명

- FR-04.1 시스템은 각 배정 쌍에 대해 코드 기반 추천 이유를 생성해야 한다.
- FR-04.2 추천 이유는 점수 계산에 사용된 상위 요인과 충돌 회피 요인을 반영해야 한다.
- FR-04.3 추천 이유 생성은 LLM 없이 `scoring.py` 또는 `matching.py`의 코드 결과를 사용해야 한다.
- FR-04.4 시스템은 인터뷰 제출 완료 시점에 기존 제출자와 신규 제출자 사이의 추천 후보를 갱신해야 한다.

### FR-05 갈등 시나리오 생성

- FR-05.1 시스템은 필요할 때만 갈등 시나리오 생성을 호출해야 한다.
- FR-05.2 갈등 시나리오 생성은 `llm_client.py`를 통해서만 Bedrock을 호출해야 한다.
- FR-05.3 LLM 호출 실패 시 시스템은 `fallback.py`의 결정론적 템플릿으로 시나리오를 생성해야 한다.
- FR-05.4 갈등 시나리오의 우선순위나 위험도 판단은 코드 기반 결과를 사용해야 하며 LLM이 결정하면 안 된다.

### FR-06 협상안 문장화

- FR-06.1 시스템은 필요할 때만 협상안 문장화를 호출해야 한다.
- FR-06.2 협상안 문장화는 갈등 요인과 학생 선호 데이터를 기반으로 해야 한다.
- FR-06.3 LLM 호출 실패 시 시스템은 `fallback.py`의 결정론적 템플릿으로 협상안을 생성해야 한다.

### FR-07 Pact 규칙 문장 생성

- FR-07.1 시스템은 필요할 때만 Pact 규칙 문장 생성을 호출해야 한다.
- FR-07.2 Pact 규칙은 배정된 두 학생의 공통 생활 규칙을 문장으로 정리해야 한다.
- FR-07.3 LLM 호출 실패 시 시스템은 `fallback.py`의 결정론적 템플릿으로 Pact 문구를 생성해야 한다.

### FR-08 Lambda 통합

### FR-08 일반 백엔드

- FR-08.1 일반 백엔드는 학생 입력, 세션 조회, 결과 조회를 처리하는 HTTP API를 제공해야 한다.
- FR-08.2 일반 백엔드는 공용 저장소에 입력 데이터를 저장하고, 필요 시 AI 백엔드를 호출해야 한다.
- FR-08.3 일반 백엔드는 AI 백엔드의 결과를 프론트엔드에 전달 가능한 구조로 변환해야 한다.
- FR-08.4 일반 백엔드는 오류 시 호출자가 처리 가능한 구조화된 응답을 반환해야 한다.
- FR-08.5 일반 백엔드는 학생 프로필 생성, 목록 조회, 단건 조회 API를 제공해야 한다.
- FR-08.6 일반 백엔드는 프로필별 생활 인터뷰 저장 및 조회 API를 제공해야 한다.
- FR-08.7 일반 백엔드는 인터뷰 저장/조회 응답에 캐릭터 분류 결과를 포함해야 한다.
- FR-08.8 일반 백엔드는 프로필별 추천 후보 조회 API를 제공해야 한다.
- FR-08.9 일반 백엔드는 매칭 요청 생성 및 수락 API를 제공해야 한다.
- FR-08.10 일반 백엔드는 채팅방 생성, 채팅방 메시지 조회 API를 제공해야 한다.
- FR-08.11 일반 백엔드는 WebSocket 기반 실시간 채팅 연결을 제공해야 한다.

### FR-09 AI 백엔드

- FR-09.1 AI 백엔드는 배정 요청을 받고 점수 계산, 매칭, 선택적 LLM 보강 결과를 조합해야 한다.
- FR-09.2 `handler.py`는 AI 요청 처리의 오케스트레이션 진입점 역할을 해야 한다.
- FR-09.3 AI 백엔드 응답 구조는 Gradio 프로토타입과 일반 백엔드가 바로 소비할 수 있는 필드를 포함해야 한다.

### FR-10 데이터 저장

- FR-10.1 시스템은 데모에 필요한 학생 설문 입력 또는 샘플 세션 데이터를 저장할 수 있어야 한다.
- FR-10.2 시스템은 생성된 배정 결과와 Pact/협상 결과를 조회 가능하게 저장할 수 있어야 한다.
- FR-10.3 저장 구조는 운영 확장을 고려하되, 해커톤 범위에서는 최소 필드만 유지해야 한다.
- FR-10.4 일반 백엔드와 AI 백엔드는 공용 키 구조와 데이터 계약을 사용해야 한다.
- FR-10.5 생활 인터뷰 응답은 프로필 ID 기준으로 조회 가능한 구조로 저장해야 한다.
- FR-10.6 단일 EC2 운영 환경에서는 PostgreSQL을 같은 인스턴스 내부에 구성하고, 일반 백엔드와 AI 백엔드가 이를 공용 저장소로 사용해야 한다.
- FR-10.7 시스템은 프로필별 추천 후보 목록과 마지막 추천 계산 시각을 저장할 수 있어야 한다.
- FR-10.8 시스템은 채팅방 메타데이터와 채팅 메시지 목록을 프로필 ID 기준으로 조회 가능한 구조로 저장해야 한다.
- FR-10.9 시스템은 같은 두 프로필 조합에 대해 중복 채팅방을 만들지 않아야 한다.
- FR-10.10 시스템은 같은 두 프로필 조합에 대해 하나의 상호 수락 상태만 유지할 수 있어야 한다.

### FR-11 서버 연결

- FR-11.1 일반 백엔드와 AI 백엔드는 각자 독립적으로 실행 가능해야 한다.
- FR-11.2 일반 백엔드는 AI 백엔드의 엔드포인트를 설정값으로 받아 연결할 수 있어야 한다.
- FR-11.3 두 백엔드 간 요청/응답 계약은 데모 전에 고정되어야 한다.
- FR-11.4 두 백엔드가 연결되지 않았을 때 일반 백엔드는 명확한 오류를 반환해야 한다.
- FR-11.5 해커톤 운영 환경에서는 단일 EC2 인스턴스 위에서 일반 백엔드와 AI 백엔드를 각각 독립 프로세스로 배포할 수 있어야 한다.
- FR-11.6 GitHub Actions를 통해 EC2로 원격 배포를 자동화할 수 있어야 한다.
- FR-11.7 외부 공개 API는 EC2의 80 포트 기준 `/api/...` 경로로 접근 가능해야 하며, 내부 애플리케이션 포트는 리버스 프록시 뒤에 숨겨져야 한다.
 - FR-11.8 외부 공개 WebSocket 연결은 EC2의 80 포트 기준 `/api/ws/...` 경로로 접근 가능해야 한다.

### FR-12 Hook 제약

- FR-12.1 저장 시 lint와 test를 실행하는 Hook 1개가 있어야 한다.
- FR-12.2 `scoring.py`, `matching.py`에 Bedrock 또는 네트워크 호출 관련 import가 없는지 검사하는 Hook 1개가 있어야 한다.
- FR-12.3 Hook은 총 2개만 유지해야 한다.

## 비기능 요구사항

- NFR-01 동일 입력에 대해 점수 계산과 배정 결과는 재현 가능해야 한다.
- NFR-02 배정 핵심 로직은 LLM 장애와 무관하게 동작해야 한다.
- NFR-03 모듈 경계는 명확해야 하며 LLM 호출 로직은 `llm_client.py`에만 위치해야 한다.
- NFR-04 구현 Task는 `requirements.md`, `design.md`, `tasks.md`에 정의된 범위 안에서만 진행해야 한다.
- NFR-05 구현 에이전트는 `requirements.md`와 `design.md`를 직접 수정하면 안 된다.
- NFR-06 데모 시간 안에 가치가 드러나도록 응답 구조는 설명 가능하고 시각화하기 쉬워야 한다.
- NFR-07 백엔드는 Gradio 프로토타입과 쉽게 연결 가능한 단순 계약을 제공해야 한다.
- NFR-08 일반 백엔드와 AI 백엔드의 책임이 겹치지 않아야 한다.
- NFR-09 공용 DB를 사용하더라도 데이터 소유권이 명확해야 한다.
- NFR-10 단일 EC2 인스턴스 배포에서도 두 백엔드의 실행, 재시작, 로그 확인 경계가 분리되어야 한다.
 - NFR-11 실시간 채팅이 일시적으로 끊겨도 기존 메시지 이력 조회는 계속 가능해야 한다.

## 작업 운영 규칙

- Kiro를 기준으로 `requirements.md`, `design.md`, `tasks.md`를 먼저 정리한 뒤 구현을 시작한다.
- 구현 Task는 Claude Code 또는 Codex가 수행할 수 있다.
- Spec과 구현 충돌이 발견되면 코드를 진행하기 전에 Spec을 먼저 갱신한다.
- 구현 완료 후 Acceptance 기준과 비교해 스스로 검토하고, 기준을 충족하면 `DONE`으로 전환한다.
